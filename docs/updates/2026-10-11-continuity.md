# 称呼确认与原话接续：怎样修复与验证

## 修复的问题

常见过程是小鲸鱼提出“以后统一叫朋友B”，本人引用回复“ok”。旧解析主要认识“以后叫我朋友B”这类直接请求，漏掉及时确认；模型口头记住了，持久记录却没有保存。群聊于是可能继续使用旧自动外号。实际读过消息、确认读完后再保存约定，也可能被错误拒绝。

## 代码怎样接通

| 环节 | 实现 | 为什么需要 |
| --- | --- | --- |
| 确认约定 | person-continuity.js 核对实际提议、同一人的及时确认、双方称呼方向与作用范围 | 她自己提议不等于朋友同意，伪造引用与别人确认不能生效 |
| 保存来源 | bridge.js 将实际展示过的记忆来源凭据与未读确认凭据分开 | 读完以后仍能保存，但未读游标权限不放宽；重启后重新读取 |
| 取用称呼 | 当前提示和控制台共用持久约定，旧自动外号留作备用 | 同一身份换群名片、换模型上下文也能接上 |
| 核对原话 | conversation-evidence.js 从当前保留消息中挑相关片段 | 不再只凭“聊过Python”的摘要猜具体措辞 |
| 工具入口 | 既有 qq_social_lookup 新增 conversation 动作，与当前轮提示共用路径 | 不增加新的工具名，不启动另一个聊天模型 |

例如同一人问“我们刚才私聊那个Python边界问题，你怎么解释的”，程序可以提供他相关的发言与她的实际回应。模型有证据接话；原话只是资料，不成为系统命令。没有保存成功时，也不能凭口头回复宣称已同步。

## 范围和限制

只有当前本人主动回顾另一个场景才触发。普通问候、主动联系和其他人的询问不读取他的私聊。明确保密及仅私聊内容不带进群里；私聊回顾群聊只取本人的直接发言和紧接的机器人回应。

只检索桥接仍保留的近期消息，默认6条、最多8条，每条最多200字符、总计1200字符，截断有标记。更早的重要结果仍依赖持久约定、共同事件及话题摘要。保密过滤较保守，邻近片段可能一起不提供。没找到时如实说明，不猜具体观点，也不声称“记得但不能说”。

## 验证到什么程度

正式目录36个顶层针对测试通过，Token economy脚本内部另有36项场景；完整回归41/42组，保留既有DSH安装工具名兼容失败。四轮真实模型用虚构身份验证新上下文称呼、按此前实际回应接话和保密限制。工程测试另外核验认证HTTP路径、原始已读状态不变、只读操作不创建记忆、身份和来源范围限制。

本机部署已核对加载版本、持久称呼和三处控制台一致。本轮没有向真实QQ发送验收消息。测试证明这些有限场景接通，不能保证所有长期聊天都正确或自然。源码副本的独立验收与远端CI结果见验收说明及仓库Actions。

运行状态、真人原始确认与恢复证据保留在本机，不随源码发布。维护时不应把整个旧备份覆盖到当前状态，也不能清空聊天和记忆来掩盖错误。
